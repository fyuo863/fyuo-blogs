# 访客缓存与异步统计：真实验证报告

测试日期：2026-09-24。本机隔离测试，不代表生产容量或零丢失承诺。

## 环境和方法

- AMD Ryzen 5 7500F，6 核 / 12 逻辑 CPU，主机约 31.54 GiB RAM。Docker Desktop 29.4.3：12 CPU、约 15.39 GiB RAM；容器未额外设置 CPU/内存配额。
- Go 1.26.2、PostgreSQL 16.14（max_connections=100）、Redis 8.6.3、Node 24.14.1。Windows 客户端，Linux Docker 后端及数据库。
- 1,000 篇合成文章，每篇 2,048 ASCII 字节。轮转首页 10 篇，列表 → 详情 → 浏览上报，无阅读停顿、自动重试、Nginx/TLS 或前端渲染。
- 对比使用同一 Compose、机器、数据集、脚本、Redis AOF everysec/noeviction、10 秒阶段、10/50/100/200 并发，计划 3 轮交替顺序。时长包含结束时在途请求排空。超过 5% 失败停止后续加压：原版触发停止，不能记作完成三轮。
- 两版本顺序运行，记录/计数随测试增加，并非冻结数据库镜像。共享机器调度、缓存及后台负载仍会影响结果；没有统计置信区间或生产容量结论。
- 原版代码为 `84f11d508a1b0217e5b46f60ee2fd5919917ec1e`；最终版为本报告同次提交的后端代码。构建时处于 dirty 工作树，原始 JSON 的 git 字段指向父提交。镜像 ID 见原始报告，二进制 SHA-256 见 [builds.json](reports/builds.json)。原版使用同一最终配置文件，但 yaml 标签缺陷仍使池字段解析为零。

## 主要结果

100 并发完整流程：原版 **89.3 次/秒**；最终版三轮 **1,835.8–1,956.5 次/秒**。200 并发原版失败 **725/1489** 次；最终版三轮 **1,929.4–2,057.3 次/秒**，没有 HTTP 错误。不要把差异归因于某一项优化：连接池、缓存和异步写入同时改变。

最终版 12 个阶段均无 HTTP 错误。事件已接收 **205,040**，去重账本新增 **205,040**，数据库 view_count 总增量 **205,040**，差值 **0**。重复响应为 0（该轮每次均生成新 ID）。请求阶段结束后约 **0.532 秒**确认队列为空，包含 Docker 查询开销，不是单事件落库延迟。

末次指标：accepted=205040、persisted=205040、failures=0、Pending=0、积压=0，数据库 MaxOpenConnections=24、WaitCount=0；见 [指标日志](reports/optimized-metrics.log)。

每一轮的吞吐、错误及各接口 P50/P95/P99 见本文末尾表格和 [受控原版数据](reports/visitor-2026-09-24T03-19-37.967Z.json)、[最终版数据](reports/visitor-2026-09-24T03-21-29.543Z.json)。成功流程表示事件已接收；持久化结论来自另一次排空后的数据库核对。

## 突发和故障恢复

最终故障组合实验得到：

- 3000 个热态突发事件（200 并发）全部接收；同一个 event_id 的 100 次重试没有额外累计。
- 实际停止 PostgreSQL：100/100 次缓存读取成功；500/500 个事件接收并形成 500 条积压。恢复后约 **3.609 秒**确认排空。
- 实际停止 Redis：正文读取 **26/32** 通过受控 SQL 回源；其余 6 次受并发保护返回 503。统计 **8/8** 返回 503，未虚假接收。
- Redis 恢复初始波次 **99/100** 暂时被拒绝；持久化基线及去重校准完成后一轮 **100/100** 成功。恢复不是瞬时无错误切换。
- 确认接收不同事件 **3602**，重复响应 **100**，新增账本及数据库增量均为 **3602**，差值 **0**。积压采样峰值 **500**，是采样下界，不是瞬时精确峰值。突发结束后约 **0.810 秒**确认排空。

热列表、同键冷回源各测试 3 波；最终故障组合验证 1 轮。冷回源是 200 并发的一次短波，不能将其瞬时 RPS 当成持续吞吐。详见 [故障原始数据](reports/resilience-2026-09-24T03-18-05.027Z.json)。

## 保留的失败轮次和原因证据

- [最初基线](reports/visitor-2026-09-24T02-43-09.090Z.json)：Redis 尚未切换 AOF，100 并发 43.7 次/秒、200 并发失败 496 次。主对比使用统一 AOF 后的受控基线。
- [中间优化版本](reports/visitor-2026-09-24T02-58-17.478Z.json) 保留，不视为最终代码结果。
- [首次故障轮](reports/resilience-2026-09-24T03-04-47.762Z.json)：停 Redis 后读取 0/32 成功。旧脚本 status=passed 仅检查最终计数，**不表示降级验收通过**；随后增加独立 150 ms Redis 探测预算并增强脚本判定。
- [第二故障轮](reports/resilience-2026-09-24T03-11-37.673Z.json)：读取降级 26/32 成功，但冷键混入突发造成 6 个 503，重建初始波次有 99 个 503。
- [预热失败轮](reports/resilience-2026-09-24T03-17-10.356Z.json)：同时预热 10 个不同冷键超过 8 个回源槽，得到 503；脚本改为顺序预热，将同键冷波次与热态突发分开测试。
- 原版池字段为零意味着没有 MaxOpen 上限且没有空闲连接复用。受控原版窗口 PostgreSQL 记录 **1,088 条 `FATAL: sorry, too many clients already`**，[日志证据](reports/postgres-baseline-errors.txt)支持本轮连接耗尽结论。
- 用户原有的 `cannot assign requested address` 还可能涉及客户端临时端口/连接 churn。本次未采集那轮 socket/TIME_WAIT/端口表，不能断言唯一根因，也不能混淆这两类错误。

## 命令、限制与简历描述

启动、迁移、测试、压测、标记保护、回滚、保留策略及配置见 [visitor-pipeline.md](visitor-pipeline.md)。未访问生产密钥、未改生产数据、未部署线上、未改全局 Docker/代理。

运行限制：AOF everysec 存在丢失窗口；跨系统没有原子提交；校准、队列满、回源保护会返回可重试 503；异常退出后持久屏障可能需要人工维护；旧客户端不传 event_id 无法幂等重试；异步记录 City 暂为空；持续忙碌时清理延后；数据库批次通过 advisory lock 串行提交。长时耐久、磁盘满/OOM/断电及任意旧备份恢复不在本次实验范围。

停止时旧点赞同步是限时尽力刷新，并不保证最后一次把所有点赞写完：本次 1,000 篇夹具的退出日志出现一条 3 秒 context deadline，随后连接正常关闭。日常定时点赞同步及真实集成测试仍通过；点赞仍依赖 Redis 持久化和原有周期落库窗口。队列/池日志是采样观测，不是持久化监控平台。

可用于简历，保留测量边界：

> 为 Go/Gin + PostgreSQL + Redis 博客实现访客缓存和异步 PV 统计：修复 Viper 连接池映射，采用 Cache-Aside、singleflight、版本屏障与有界回源；使用 Redis Stream/Consumer Group 承接突发，通过 event_id 唯一约束和数据库事务实现幂等落库、Pending 重领与背压。在同机 Docker、1,000 篇合成文章的短时测试中，100 并发完整访客流程由约 89 次/秒提升至 1,836–1,957 次/秒；205,040 个已接收事件全部落库，计数差值为 0，并验证停库恢复及提交后未 ACK 的重放。

不可改写为生产容量或绝对零丢失。
